# Распознавание активности пользователя по данным датчиков

Мобильное приложение для Android, которое непрерывно определяет тип активности
пользователя методами машинного обучения и ведёт журнал.

Используются все пять датчиков из задания:

| Датчик | Роль в распознавании |
|---|---|
| Акселерометр | основной сигнал: амплитуда и ритм движения |
| Гироскоп | вращение корпуса — отличает велосипед и повороты от прямой ходьбы |
| Магнитометр | изменение курса; косвенно — близость к металлу (транспорт) |
| Датчик приближения | телефон перекрыт: карман, сумка, у уха |
| Датчик освещённости | темно (карман) или светло (в руке) |

**Распознаваемые классы активности:** покой, ходьба, бег, подъём по лестнице,
спуск по лестнице, поездка в транспорте, велосипед.

**Распознаваемое положение телефона:** в кармане, в руке, у уха, на столе.

---

## Как это работает

```
5 датчиков  ──►  SensorHub  ──►  SlidingWindowBuffer  ──►  FeatureExtractor  ──►  2 модели  ──►  сглаживание  ──►  журнал
   разные          единая         окна 128 отсчётов          9 каналов              TFLite          EMA +           Room:
   частоты        сетка 50 Гц      (2.56 с, 50 % пере-      + 16 признаков                        гистерезис      окна +
                                    крытия)                                                                      интервалы
```

1. **Синхронизация.** Датчики Android отдают события с разной и плавающей
   частотой. `SensorHub` приводит их к единой сетке 50 Гц: акселерометр задаёт
   такт, остальные каналы подставляются последним известным значением. Там же
   фильтром нижних частот выделяется вектор гравитации — он отделяет *ориентацию*
   телефона от собственно *движения*.

2. **Нарезка на окна.** Кольцевой буфер выдаёт окна по 128 отсчётов (2.56 с)
   со сдвигом 64 (перекрытие 50 %). Это стандартная геометрия датасетов HAR,
   и приложение специально ей следует, чтобы обучаться на публичных данных.

3. **Признаки.** Для активности в сеть подаются сырые каналы движения — свёртки
   сами находят форму шага. Для положения телефона считаются 16 агрегированных
   признаков, где ключевую роль играют приближение, освещённость и стабильность
   ориентации. Дополнительно считается интерпретируемая сводка окна (частота
   главного пика, спектральная энтропия, наклон) — она показывается в UI и
   пишется в журнал, чтобы решение модели можно было объяснить постфактум.

4. **Две модели TensorFlow Lite.**
   * *Активность* — сеть с **двумя входами**: свёрточная ветка по каналам
     движения (Conv1D 64→128→128, GlobalAveragePooling) и полносвязная ветка
     по 16 контекстным признакам, после чего ветки объединяются.
     Вторая ветка — это и есть механизм, которым освещённость и приближение
     влияют на определение активности: один и тот же рисунок ускорения
     означает разное, когда телефон в кармане и когда лежит на столе.
   * *Положение телефона* — MLP по тем же 16 признакам.

5. **Сглаживание.** Решения принимаются каждые 1.28 с, и без сглаживания класс
   дребезжит на переходах. Применяется экспоненциальное сглаживание вектора
   вероятностей плюс гистерезис: смена класса требует уверенного перевеса.

6. **Журнал.** Пишутся два уровня: покадровый (каждое окно со всеми признаками)
   и агрегированный (соседние окна одного класса слиты в интервал —
   «Ходьба, 10:31–10:47, 16 мин»). Оба выгружаются в CSV.

### Если модель ещё не обучена

Приложение собирается и работает **до** обучения модели: при отсутствии
`.tflite` в assets включается эвристический классификатор на явных правилах
(пороги по СКЗ ускорения, частоте главного пика, спектральной энтропии,
освещённости и датчику приближения). Он различает меньше классов — покой,
ходьбу, бег, транспорт, велосипед, но не лестницу — и честно сообщает об этом
в интерфейсе. Заодно он служит базовой линией, с которой сравнивается нейросеть.

## Сборка

### Требования

* **JDK 21** (LTS). Версия принципиальна: проект собирается Gradle 8.9,
  который не поддерживает JDK 25 — а именно JDK 25 встроен в Android Studio
  2026.1 как JBR. См. «Настройка JDK» ниже.
* **Android SDK**: Platform 35, Build-Tools 35.0.0, Platform-Tools.
  minSdk 26 (Android 8.0).
* **Android Studio** — не обязательна для сборки, нужна для отладки и запуска на устройстве.
* Телефон с акселерометром; остальные датчики опциональны — их отсутствие
  снижает качество, но не ломает приложение.

### Сборка из командной строки

```bash
./gradlew testDebugUnitTest    # модульные тесты обработки сигнала
./gradlew assembleDebug        # APK в app/build/outputs/apk/debug/
./gradlew installDebug         # установка на подключённый телефон
```

Нужны переменные окружения `JAVA_HOME` (на JDK 21) и `ANDROID_HOME`
(на каталог SDK), либо файл `local.properties` со строкой:

```properties
sdk.dir=C:/Users/<имя>/AppData/Local/Android/Sdk
```

Слэши в `local.properties` — прямые. В формате `.properties` обратный слэш
является символом экранирования, и путь вида `C:\Users\...` разберётся
неверно; сборка упадёт с «синтаксической ошибкой в имени файла».

### Настройка JDK в Android Studio

Android Studio 2026.1 по умолчанию использует встроенный JBR 25, на котором
Gradle 8.9 не запускается. После открытия проекта:

*Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK* → выбрать **JDK 21**.

Затем `Run → Run 'app'` на подключённом телефоне.
Эмулятор не подойдёт: у него нет настоящих датчиков движения.

### Смена имени пакета

Сейчас пакет `com.example.har` — это заведомая заглушка. Для публикации
замените его через `Refactor → Rename` на модуле и поправьте `applicationId`
и `namespace` в `app/build.gradle.kts`.

## Обучение модели

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  на Linux/macOS: source .venv/bin/activate
pip install -r ml/requirements.txt

python ml/train.py --source all
```

Источники данных (`--source`):

| Значение | Что берётся |
|---|---|
| `uci` | только UCI HAR — быстро, но телефон всегда на поясе |
| `realworld` | только RealWorld HAR — 15 человек, 6 позиций на теле, есть освещённость |
| `own` | только ваши записи из вкладки «Сбор данных» |
| `both` | `uci` + `own` |
| `all` | всё сразу — **рекомендуется** |

Первый запуск с `realworld` или `all` качает около 1.5 ГБ (по архиву на связку
«человек — датчик — активность») и кэширует их в `ml/data/realworld`;
повторные запуски ничего не скачивают.

Скрипт сам скачает **UCI HAR Dataset** (30 человек, 50 Гц, окна 2.56 с — ровно
та геометрия, которую использует приложение), обучит сеть, сконвертирует её в
TensorFlow Lite и положит результат в `app/src/main/assets/`:

* `activity_model.tflite`
* `placement_model.tflite` (только если есть собственные размеченные записи)
* `model_meta.json` — список каналов, список классов, статистики нормировки,
  точность на тесте

После этого пересоберите APK — модели попадут внутрь.

### Фактический результат обучения

Три источника: UCI HAR (10 299 окон, 30 человек, пояс), RealWorld HAR
(276 590 окон, 15 человек, 6 позиций на теле) и собственные записи
с телефона (736 окон). Всего 287 625 окон; обучение 139 142 /
валидация 61 093 / тест 87 390, деление по людям.

**Активность** — 6 классов:

```
              precision  recall  f1-score  support
       STILL       0.87    0.99      0.93    39737
     WALKING       0.77    0.64      0.70    12318
     RUNNING       1.00    0.73      0.84    17026
   STAIRS_UP       0.66    0.62      0.64    11231
 STAIRS_DOWN       0.67    0.79      0.73     6914
     CYCLING       0.90    1.00      0.95      164

Accuracy: 0.8293     Размер модели: 420 КБ
```

### Почему 0.83, а не прежние 0.99

Предыдущая версия, обученная почти целиком на UCI HAR, показывала 0.9856 —
но UCI HAR снят **только с пояса**, и телефон в кармане или в руке она
не видела никогда. Новый тест содержит шесть положений на теле, и цифра
честно отражает более трудную задачу.

Разбивка по позициям показывает, что размен выгодный:

```
  uci:waist     0.9879   ← пояс, лабораторные условия
  rw:upperarm   0.8583
  rw:chest      0.8364
  rw:waist      0.8250
  rw:head       0.8187
  rw:forearm    0.8119   ← примерно «в руке»
  rw:thigh      0.8059   ← примерно «в кармане»
  own:POCKET    0.9111   ← наши записи
```

На поясе новая модель даёт **0.9879 против 0.9856** у прежней
специализированной — то есть не хуже, — и дополнительно покрывает шесть
положений, которых та не видела. Для приложения, где телефон лежит
в кармане или в руке, это однозначное улучшение.

Главная оставшаяся путаница — ходьба против лестницы (2877 окон ходьбы
опознаны как подъём) и бег против покоя (3237 окон). Второе выглядит
странно и заслуживает разбора: вероятно, записи бега в RealWorld содержат
паузы, попавшие под метку «бег».

**Положение телефона** — тест 471 окно:

```
              precision  recall  f1-score  support
      POCKET       0.82    0.79      0.80      191
     IN_HAND       0.00    0.00      0.00        0
      AT_EAR       0.86    0.88      0.87      280
    ON_TABLE       0.00    0.00      0.00        0

Accuracy: 0.8408     Размер модели: 15 КБ
```

Эту цифру нельзя принимать за чистую монету:

* **`IN_HAND` и `ON_TABLE` в тесте отсутствуют** (support = 0). Они есть
  только в собственных записях — 42 и 58 окон, и все попали в обучение.
  Строка нулей означает «не проверено», а не «не работает»; скрипт печатает
  об этом отдельное предупреждение.
* Фактически это классификатор «карман против уха».
* `AT_EAR` в RealWorld — это устройство на **ремне на голове**, а не телефон
  у уха. Ориентация похожа, но это осознанное допущение, а не настоящая метка.
* Классы пришлось выравнивать: RealWorld даёт по 46 тысяч окон на класс,
  свои записи — десятки. При соотношении 1000:1 взвешивание уже не помогает,
  поэтому крупные классы урезаются (`--placement-cap-ratio`).

Класс «транспорт» по-прежнему отсутствует: его нет ни в одном из трёх
источников. Он есть в датасете SHL, но тот весит около 270 ГБ.

### Вклад освещённости и приближения измеряется, а не декларируется

Скрипт обучения после оценки прогоняет модель повторно, подав вместо
контекстных признаков нули (то есть среднее обучающей выборки), и печатает
разницу. Приложение показывает её на экране «О модели».

Абляция считается по группам признаков, а не только для контекста целиком:
общий вклад ничего не говорит о конкретных датчиках, потому что ориентация
и статистики движения выводятся из акселерометра, а освещённость
и приближение — отдельные измерения.

```
без «весь контекст»:  0.5988  (вклад +0.2305)
без «ориентация»:     0.8240  (вклад +0.0053)
без «освещённость»:   0.8258  (вклад +0.0035)
без «приближение»:    0.8277  (вклад +0.0016)
```

Читается так: **контекстная ветка решает очень много** — без неё точность
падает на 23 пункта. Но почти весь этот вклад дают агрегированные
статистики движения (СКЗ линейного ускорения, разброс вращения), а не
датчики освещённости и приближения. Их собственный вклад — **+0.35 и
+0.16 пункта**: измеримый, но малый.

История цифры по освещённости: ровно 0.0000 на одном UCI HAR (где её нет),
+0.24 после добавления собственных записей, +0.35 после RealWorld HAR.

Чтобы вклад вырос дальше, нужны записи **одной и той же активности
в разных положениях телефона** — ходьба в кармане против ходьбы в руке
при разном освещении. Тогда рисунок ускорения похож, и различить случаи
может только контекст.

### Оговорка про датчик приближения на этом устройстве

В записях с Nothing Phone (A059) датчик приближения оказался **перекрыт
0.0–0.4 % времени даже в «карманных» записях**, хотя ожидалось около 100 %.
Вероятная причина — датчик под экраном отключается при погашенном экране.
Практический вывод: на этом устройстве «в кармане» определяется по
освещённости (медиана 0 лк — сработала), а приближение бесполезно.
Признак `prox_near_ratio` в контексте есть, но информации не несёт.

### Три выборки, а не две

Валидация используется для ранней остановки, то есть модель косвенно
подстраивается под неё. Поэтому испытуемые делятся на три непересекающиеся
группы, и тестовая смотрится ровно один раз — в финальном отчёте.
При делении на две группы (когда тест же служит валидацией) та же модель
показывала 0.9699, и эта цифра была бы завышенной.

### Собственные данные

Публичные датасеты не содержат ни магнитометра, ни датчиков приближения и
освещённости, и в них нет классов «бег», «транспорт», «велосипед». Модель
положения телефона обучать на них вообще не на чем. Поэтому в приложении есть
вкладка **«Сбор данных»**: выбираете активность и положение телефона, нажимаете
«Начать запись» — и приложение пишет сырые показания всех пяти датчиков в CSV
с этой меткой.

```bash
# выгрузить записи с телефона (или отправить их себе кнопкой «Поделиться»)
adb pull /data/data/com.example.har/files/datasets ml/data/own

python ml/train.py --source both --epochs 60      # UCI + свои данные
python ml/evaluate.py --own-dir ml/data/own       # проверка именно .tflite
```

Состав каналов и список классов определяются данными, а не зашиты в код:
что получилось — записывается в `model_meta.json`, и приложение подстраивается.
Обучение только на UCI HAR даёт 6 каналов и 4 класса; добавление своих записей
поднимает это до 9 каналов и всех 7 классов.

### Почему деление выборки — по людям

Соседние окна перекрываются на 50 %, поэтому при случайном делении почти у
каждого тестового окна есть почти-дубликат в обучении. Точность выходит 97–99 %
и не имеет никакого отношения к работе на новом человеке. `split_by_subject`
делит выборку по испытуемым (для собственных записей — по файлам), и цифры в
`model_meta.json` — честные.

## Технические решения и их причины

**Почему окно 2.56 с, а не короче.** Шаг человека длится 0.5–1 с. Чтобы
надёжно оценить его частоту, нужно 2–3 периода. Более короткое окно снижает
задержку, но частотные признаки становятся бесполезными.

**Почему передний сервис, а не WorkManager.** Распознавание требует
непрерывного потока с датчиков; WorkManager даёт отложенные задачи с
минимальным интервалом 15 минут и для этого не годится. Без переднего сервиса
Android усыпляет процесс через несколько минут, и журнал получается дырявым.

**Почему две отдельные модели, а не одна многозадачная.** Активность и
положение телефона нужны в разном разрешении и обучаются на разных данных:
активность — на публичном датасете, положение — только на собственных записях.
Одна сеть с двумя головами потребовала бы, чтобы каждая запись была размечена
и тем, и другим.

**Почему решение принимается по вектору вероятностей, а не по argmax.**
Полное распределение пишется в журнал и показывается в UI. Без него спорный
случай («ходьба 0.34 против велосипеда 0.33») выглядит так же, как уверенный,
и отладить классификатор на живом устройстве невозможно.

**Почему в журнале два уровня.** Покадровый нужен для анализа и пересчёта
метрик, интервальный — для человека: список из тысяч строк по 1.28 с нечитаем.

### Задержка медленных датчиков

Магнитометр, датчики приближения и освещённости событийные: до первого
события держатся начальные значения (нули и −1). Замер на устройстве:
первое событие магнитометра — через 0.04 с, освещённости — через 0.26 с.
То есть артефакт задевает 13 кадров из 128 только в самом первом окне
после запуска. Для обучения это пренебрежимо, но при анализе первых секунд
записи об этом стоит помнить.

**Известные ограничения по существу:**
* **Домашний разрыв между UCI HAR и приложением.** Сигналы в UCI HAR
  предварительно отфильтрованы (медианный фильтр и ФНЧ 20 Гц), а приложение
  подаёт сырые данные. При 50 Гц эта разница невелика (частота Найквиста 25 Гц),
  но она есть. Надёжный способ её убрать — дообучить модель на собственных
  записях (`--source both`).
* **Лестница.** Подъём и спуск по лестнице — самые трудные классы в HAR;
  они путаются с обычной ходьбой. Эвристический классификатор их не различает
  вовсе и не делает вид, что различает.
* **Датчик приближения у большинства телефонов бинарный** (0 или maximumRange),
  поэтому признак «перекрыт» — это порог, а не расстояние.
* Без магнитометра, датчика приближения или освещённости соответствующие
  признаки подаются нулями; приложение показывает список отсутствующих датчиков
  на главном экране.
* Батарея: непрерывный опрос на 50 Гц заметно её расходует. Для длительного
  наблюдения имеет смысл снизить `SAMPLE_RATE_HZ` и переобучить модель на той
  же частоте.
